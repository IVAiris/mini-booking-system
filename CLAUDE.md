## 4. Инженерные конвенции и что нельзя добавлять без явной задачи
(источник: `spec.md` разделы 3, 5, 6, 8; `Plan.md` «Правила работы с планом»)

**Устоявшиеся конвенции — auth-lite (соблюдать по умолчанию):**
- Пароль хешируется bcryptjs, 12 раундов; открытый пароль не логируется и не хранится.
- Проверка роли (`requireRole`) и сессии (`getCurrentUser`) выполняется только на сервере (`lib/auth.ts`), не полагаться на скрытие UI-элементов.
- Мутации — через Server Actions (`"use server"`), без middleware (`middleware.ts` для ролей/сессии не используется).
- Session-токен — в cookie, запись в таблице `Session` — источник истины о валидности.
- Публичная регистрация всегда создаёт роль `user`; поле `role`, если оно передано в запросе, сервер игнорирует.
- Ошибка валидации email при регистрации — точная формулировка «Введите корректный адрес электронной почты».

**Устоявшиеся конвенции — слой данных (текущий цикл, `Plan.md`):**
- В этом цикле работать только со слоем данных и бэкендом (модели Prisma, миграции, seed, Server Actions, серверные проверки) — без новых экранов и интерфейсов.
- Не настраивать внешний контур уведомлений (email/push/сторонние сервисы) — только внутренние уведомления (`Notification` в БД), в будущем отображаемые в личном кабинете.
- Не добавлять новые роли, статусы брони или сущности сверх зафиксированных в `spec.md` (`user`/`admin`/`super_admin`; `pending`/`confirmed`/`cancelled`; `User`/`Slot`/`Booking`/`Notification`) без отдельного согласования с пользователем.
- Роль остаётся enum-полем `User.role`; отдельная таблица `Role` не вводится.
- Слот считается занят, если по нему есть хотя бы одна бронь со статусом `pending`/`confirmed`; проверка эксклюзивности слота — на уровне приложения в транзакции, не через DB-уровневый partial unique index.
- Переход статуса брони проверяется явно в коде (только `pending→confirmed`, `pending→cancelled`, `confirmed→cancelled`) — не полагаться на то, что enum-тип поля сам ограничивает допустимые переходы.

**Нельзя добавлять без явной задачи:**
- Новые экраны/интерфейсы для слотов, бронирований, уведомлений (текущий цикл — только данные и бэкенд; UI — отдельная будущая задача).
- Внешний контур уведомлений (email/push/сторонние интеграции).
- Новые роли, статусы брони или сущности сверх зафиксированных в `spec.md` без согласования.
- Middleware-based route protection (`middleware.ts`) для ролей/сессии.
- Сторонние auth-библиотеки (NextAuth.js/Auth.js).
- Изменение зафиксированной версии Prisma (6.19.3) на диапазон или другую версию.
- Разграничение прав `admin` vs `super_admin`.
- Скрытие пунктов навигации по роли.

## 6. Проверки после изменений
Автоматических тестов и CI в проекте нет. Актуальный список проверок смотреть в `package.json` → `scripts` (сейчас: `dev`, `build`, `start`, `lint`). При отсутствии проверки под конкретный сценарий — проверять вручную (например, через `npm run dev`, прямой запрос к БД или вызов Server Action на тестовых данных).

**Обязательное правило при прямых запросах к БД (`psql`, скрипты, Prisma-запросы для ручной проверки):**
- Никогда не печатать в чат/вывод `DATABASE_URL` или пароль из `.env` — ни через `grep`/`cat .env`, ни встраивая строку подключения в команду, которая будет видна пользователю. Загружать переменную окружения в shell-переменную можно, но саму переменную не печатать и не подставлять в текст команды, показываемой пользователю.
- Для проверок, не требующих конкретных значений (наличие записей, регрессия auth-lite и т.п.), использовать агрегатные запросы (`COUNT(*)`, `EXISTS`) вместо `SELECT *`/выборки конкретных колонок с персональными данными (email, имя и т.п.).
- Прецедент: на Шаге 2 цикла «слой данных» пароль БД и email пользователей были выведены в чат в открытом виде при верификации миграции — исправлено переходом на агрегатные запросы без утечки (см. `Plan.md`, Шаг 2, поле «Ошибки»). Не повторять на последующих шагах, которые тоже трогают БД напрямую (Шаги 3–6).

## 7. Рабочие правила
(источник: `Plan.md` «Правила работы с планом»)
- Работать по одному активному шагу `Plan.md` за раз; не начинать следующий, пока текущий не помечен ✅ или проблема не зафиксирована как принятый риск.
- Перед изменением кода — сначала показать план изменения файлов (что и зачем меняется), затем вносить правки; не менять результат без согласования пользователя, даже если есть более эффективный вариант (см. навык `change-approval`).
- После реализации каждого шага — явно указать способ его локальной проверки (конкретная команда/сценарий, не общая фраза) и сразу обновить блок шага в `Plan.md` (факт выполнения, Проверка, Ошибки).
