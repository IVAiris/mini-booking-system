# Mini Booking System

Учебный сервис онлайн-записи на слоты. Реализовано два модуля:

- **auth-lite** — регистрация, вход по email/паролю, серверные сессии и минимальный контроль доступа по ролям (`user`/`admin`/`super_admin`).
- **Слой данных** — модели `Slot`/`Booking`/`Notification`, статусы брони (`pending`/`confirmed`/`cancelled`) и серверные проверки (роль, владение бронью, доступность слота, допустимые переходы статуса). На этом шаге — только данные и бэкенд: своего UI у слотов/броней/уведомлений пока нет, операции доступны программно (Server Actions в `app/actions/bookings.ts`) и проверяются вручную (см. «Смоук-тест слоя данных» ниже).

## Стек

Next.js 16.3.1, React 19.2.8, TypeScript, Tailwind CSS 4, Zod, Prisma/`@prisma/client` 6.19.3 (точная версия), bcryptjs, PostgreSQL, npm.

## Запуск локально

1. Установить зависимости:

   ```bash
   npm install
   ```

2. Скопировать `.env.example` в `.env` и заполнить реальными значениями:

   ```bash
   cp .env.example .env
   ```

   - `DATABASE_URL` — строка подключения к локальной PostgreSQL.
   - `SEED_SUPER_ADMIN_NAME` / `SEED_SUPER_ADMIN_EMAIL` / `SEED_SUPER_ADMIN_PASSWORD` — данные единственного `super_admin`, создаваемого seed-скриптом (пароль ≥8 символов).

3. Применить миграции:

   ```bash
   npx prisma migrate dev
   ```

4. Засеять стартовые данные — единственного `super_admin` и один демо-`Slot` (идемпотентно — повторный запуск не создаёт дубликаты):

   ```bash
   npx prisma db seed
   ```

5. Запустить dev-сервер:

   ```bash
   npm run dev
   ```

   Открыть [http://localhost:3000](http://localhost:3000).

## Роли

| Роль | Как появляется | Что доступно на этом шаге (auth-lite) |
|---|---|---|
| `guest` | любой неавторизованный посетитель | открыть формы регистрации и входа, создать учётную запись, войти |
| `user` | публичная регистрация через `/register` — единственный способ, поле `role` в запросе игнорируется | войти в свой аккаунт (`/account`), видеть первый контур будущих записей и уведомлений (карточка «Мои записи») |
| `admin` | назначается вне публичной регистрации — вручную (например, через Prisma Studio) или сидом | то же, что `user`, плюс карточки «Слоты администратора» и «Записи администратора» на `/account`, доступ к `/admin` |
| `super_admin` | ровно один экземпляр, создаётся только seed-скриптом (`npx prisma db seed`) | то же, что `admin` |

На этом шаге `admin` и `super_admin` функционально идентичны — различаются только маркировкой и происхождением аккаунта; разграничение прав между ними не реализовано (запланировано на будущий шаг, вне auth-lite).

Основной сценарий: гость регистрируется → сервер создаёт `User` с ролью `user` и хешем пароля → сессия сохраняется → пользователь открывает `/account` и видит свой профиль и роль.

## Тестовые данные

- **`super_admin`** — email/пароль берутся из `.env` (`SEED_SUPER_ADMIN_EMAIL`/`SEED_SUPER_ADMIN_PASSWORD`), аккаунт создаётся командой `npx prisma db seed`.
- **`user`** — тестового аккаунта в комплекте нет; создаётся через форму `/register` (любой email/пароль, соответствующие валидации: имя ≥2 символов, пароль ≥8 символов с буквой).
- **`admin`** — на этом шаге нет ни seed-данных, ни UI для создания; роль можно выставить вручную через Prisma Studio (`npx prisma studio` → таблица `User` → поле `role`).
- **Демо-`Slot`** — один слот (01.09.2026, 10:00–11:00 UTC) создаётся тем же `npx prisma db seed`, для ручной проверки брони.

## Слой данных: слоты, брони, уведомления

На этом шаге нет собственного UI и нет read/query-операций (только запись) — только модели, серверные операции и проверки. Посмотреть данные и проверить логику можно так:

- **Посмотреть текущее состояние БД** — `npx prisma studio` (таблицы `Slot`, `Booking`, `Notification`).
- **Вызвать операции программно** — три функции в `lib/bookings.ts` (`createBooking`, `confirmBooking`, `cancelBooking`), обёрнутые в Server Actions в `app/actions/bookings.ts`; каждая принимает актёра (`{id, role}` текущего пользователя) и проверяет права/статус/доступность слота на сервере, до изменения данных.

**Правила статусов и ролей** (кратко; полная матрица — в истории проекта):
- Бронь проходит `pending → confirmed → cancelled`; `pending → cancelled` — тоже допустимо; любой другой переход отклоняется.
- Создать бронь может только `user`, только для себя, только на слот без другой активной (`pending`/`confirmed`) брони.
- Подтвердить бронь может только `admin`/`super_admin`.
- Отменить бронь: `admin`/`super_admin` — любую; `user` — только свою и только в статусе `pending`.
- При создании брони и при каждой смене статуса создаётся уведомление (`Notification`) владельцу брони.

**Известные ограничения этого шага** (не баги, осознанно вне scope):
- Нет операции создания `Slot` через приложение — слоты появляются только через `prisma/seed.ts` или вручную (Prisma Studio).
- Роль `admin` (в отличие от `super_admin`) нигде не создаётся автоматически — в проекте пока нет ни одного аккаунта с этой ролью.

## Smoke-тест auth-lite

Ручной прогон критериев готовности модуля auth-lite. Выполнен и подтверждён на этом шаге:

| # | Критерий | Как проверено | Результат |
|---|---|---|---|
| 1 | Публичная регистрация создаёт пользователя строго с ролью `user`, даже если в запросе передано другое значение `role` | Регистрация через `/register` с полем `role=super_admin` в теле запроса | Роль в БД — `user`; пароль сохранён как bcrypt-хеш (12 раундов), не в открытом виде |
| 2 | Вход выдаёт рабочую серверную сессию (`Session` + cookie); выход её инвалидирует | Вход через `/login` → запись `Session` + `httpOnly` cookie; выход кнопкой «Выйти» на `/account` | Cookie получает истёкший срок действия, запись `Session` удаляется из БД; повторный запрос с тем же (уже недействительным) cookie получает отказ |
| 3 | `/account` недоступна без авторизации, показывает данные только владельца сессии | Запрос к `/account` без cookie; запрос с валидной сессией | Без сессии — редирект на `/login`; с сессией — отображаются имя/email именно вошедшего пользователя |
| 4 | Обращение к административному разделу без роли `admin`/`super_admin` блокируется на сервере, независимо от видимости пункта меню | Пользователь с ролью `user` (пункт «Админка» виден в навигации) переходит на `/admin` | Сервер отвечает `404` (`requireRole` вызывает `notFound()`), без сессии — сначала редирект на `/login` |
| 5 | После запуска seed в БД существует ровно один `super_admin`; повторный запуск seed не создаёт второго | `npx prisma db seed` запущен дважды подряд | Первый запуск создаёт `super_admin`, второй — выводит «уже существует, пропускаю создание»; в БД ровно одна запись с ролью `super_admin` |
| 6 | Prisma и `@prisma/client` зафиксированы версией `6.19.3` без диапазонов | `package.json` → `dependencies`/`devDependencies` | `"prisma": "6.19.3"`, `"@prisma/client": "6.19.3"` — точные версии, без `^`/`~` |

Все 6 критериев пройдены.

## Smoke-тест слоя данных

Ручной прогон критериев готовности модуля «слой данных» (через `lib/bookings.ts`, без UI). Выполнен и подтверждён на этом шаге:

| # | Критерий | Как проверено | Результат |
|---|---|---|---|
| 1 | Модели `Slot`, `Booking`, `Notification` и статусы брони реализованы по контракту, миграция применена без потери данных auth-lite | `npx prisma migrate dev`, затем прямой запрос к БД | Таблицы созданы; пользователи и сессии auth-lite не повреждены (3 пользователя, 1 `super_admin` — как до миграции) |
| 2 | Бронь проходит только допустимые переходы (`pending→confirmed`, `pending→cancelled`, `confirmed→cancelled`); любой другой переход отклоняется | Полный цикл `pending→confirmed→cancelled`; попытка повторного перехода из `cancelled` | Полный цикл проходит с созданием уведомления на каждом шаге; повторный переход из `cancelled` отклонён с ошибкой |
| 3 | Бронь нельзя создать на слот, у которого уже есть активная (`pending`/`confirmed`) бронь | Создание второй брони на уже забронированный слот | Отклонено («Слот уже занят»); после отмены брони слот снова доступен |
| 4 | `user` не может изменить статус чужой брони или выполнить действие вне своей роли (`admin`-действия) ни при каком запросе | `user` пытается подтвердить/отменить чужую бронь; `user` пытается подтвердить свою же бронь; `admin` пытается создать бронь от своего лица | Все три попытки отклонены на сервере с понятной ошибкой, БД не изменена |
| 5 | При создании брони и при каждой смене статуса создаётся ровно одна запись `Notification` для владельца брони | Полный цикл брони + проверка количества и `userId` уведомлений | 3 уведомления на полный цикл, все принадлежат владельцу брони (не инициатору действия) |
| 6 | Регрессий в auth-lite нет | `npm run dev` + реальные HTTP-запросы: регистрация, вход (верный/неверный пароль), `/account`, `/admin`, выход | Все сценарии работают как до начала этого модуля; тестовые данные удалены после проверки |

Все 6 критериев пройдены. Известные ограничения этого шага (не проверяются, т.к. кода для них нет) — см. «Известные ограничения» выше.
